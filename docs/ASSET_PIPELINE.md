# Asset Pipeline: visual production of game templates

Date: July 31, 2026.
Status: mandatory work instructions for the agent. Priority is higher than local decisions inside the renderer code.
Related documents: `PHASER_MVP_IMPLEMENTATION_PLAN.md` (section 8), `VISUAL_PALETTE.md`, `GAME_REDESIGN_PIPELINE.md`.

## 0. Reason for the appearance of the document

Comparison `design-references/*` s `output/playwright/*` showed systemic visual degradation in all games:

- the background fades to almost white (opacity is suppressed);
- 3D-podiums, glass domes, chamfers and shadows are replaced by flat rectangles with thin outlines;
- illustrations within zones are reduced to a single pale line;
- the composition loses density: huge empty panels, tiny cards;
- The mascot shrinks and moves into a corner.

Root cause: decorative elements are drawn with primitives `Phaser.GameObjects.Graphics`. It is impossible to reproduce a raster reference with vector primitives. This document changes production technology.

## 1. The main rule

**Code never paints beauty. The code collects ready-made PNG assets and animates them.**

Prohibited use `Graphics`/`fillRect`/`lineStyle`/`arc` for:

- backgrounds and background layers;
- podiums, domes, trays, panels, cards;
- decorative illustrations (graphs, atoms, feathers, etc.);
- mascot

`Graphics` allowed only for: thin interactive states (drag line, magnetic arc, hit backlight), masks and debug mode.

Text, formulas and custom images remain a DOM overlay - this decision does not change.

## 2. Channels for obtaining assets

Process limitation: The pipeline is completely self-contained. Manual cutting of references by humans is not used; The Product Owner is only involved in the final acceptance/rejection process.

### Channel A - autonomous generation of objects individually (main)

Never generate the entire scene. Each decorative object is produced separately:

1. Generating an object on a clean background (Recraft https://recraft.ai or SDXL-compatible API). Reference from `design-references/<game>/` served as a style sample (image-to-image / style reference), and not as a source of cutting.
2. Prompt formula: `<object>, <material/style from reference>, soft 3D render, casual educational game asset, isolated on plain background, no text`. Example: `glass dome podium with thick green rim, frosted glass, soft studio light, isolated`.
3. Automatic background removal: `rembg` (locally, `pip install rembg`) or transparent Recraft background.
4. Automatic downscale/optimize to @2x target logical size (sharp/squoosh-cli, oxipng).
5. The background plate is generated by a separate image without objects (norm: `design-references/group-sort/classroom-background-plate-v1.png`).

Style control between generations: the same style-reference and the same prompt tail for all objects of the same game; objects that do not pass the vision judge under the “style unity” point (section 11) are regenerated.

### Channel B - generative completion of the background

If after layout seams or holes in the background are visible, the background is regenerated entirely as a single plate; no manual retouching is used.

### Channel B - ready-made CC0/free packs (addition)

- Kenney (https://kenney.nl/assets): UI Pack, Particle Pack - panels, buttons, particle textures, CC0.
- CraftPix freebies (https://craftpix.net/freebies/) - casual 2D packs.
- itch.io game assets with filter by license.

Each external or generated asset is recorded in the registry of origin (see. `PHASER_MVP_IMPLEMENTATION_PLAN.md`, section 8.4): source, license, model/author, date, conversions.

## 3. Technical delivery format

### 3.1. Directory structure

```text
public/game-assets/
  common/
    particles/ # stars, sparks, confetti (burst textures)
    mascot/ # sprite sheet or Corgi Rive file
  games/
    group-sort/
      atlas.png           # texture atlas
      atlas.json          # Phaser atlas JSON
      background.png # background-plate, separately (large)
      manifest.json # see 3.4
    match-pairs/ ...
    quiz-rush/ ...
    recall-deck/ ...
    mistake-arena/ ...
    force-lab/ ...
```

### 3.2. Atlases

- Assembly: free-tex-packer (https://free-tex-packer.com) or `npx free-tex-packer-cli`, Phaser 3 format (compatible with Phaser 4).
- All small and medium sprites of the game are included in one atlas; background - a separate file.
- Budgets from the plan are saved: essential assets of the first scene ≤1.5 MB desktop / ≤900 KB mobile; Run PNG through oxipng/squoosh.

### 3.3. Nine-slice is a must-have technique for panels

All stretchable surfaces (cards, trays, HUD panels, response tiles) are supplied as one PNG with a baked shadow/bevel/round and are rendered via `Phaser.GameObjects.NineSlice`. This gives “expensive” panels of any size without distorting the corners. Flat rectangles with a stroke instead of nine-slice - autoregression, does not pass review.

### 3.4. Game manifesto

```json
{
  "game": "group-sort",
  "version": 1,
  "background": { "key": "bg", "file": "background.png", "minAlpha": 0.85 },
  "atlas": { "key": "gs", "image": "atlas.png", "data": "atlas.json" },
  "nineSlice": {
    "card": { "frame": "card", "slice": [24, 24, 24, 24] },
    "tray": { "frame": "tray", "slice": [40, 40, 32, 48] }
  },
  "provenance": "docs/asset-provenance/group-sort.md"
}
```

## 4. Numerical style guide (complements VISUAL_PALETTE.md)

The agent interprets adjectives (“light”, “airy”) as “all white”. Required numbers:

| Parameter | Meaning |
| --- | --- |
| Background plate transparency | alpha ≥ 0.85; it is forbidden to extinguish the background below |
| Clean `#FFFFFF` on playing surfaces | prohibited; minimum light gradient/tinting from the palette |
| Card/Panel Shadow | baked into sprite; equivalent offset-y 6–10 px, blur 18–24 px, black 12–18% |
| Filling a frame with content (desktop) | ≥ 70% usable area; empty panels larger than 25% of frame - regression |
| Mascot | ≥ 16% frame height on desktop; not “in the corner like a sticker”, but on a pedestal/in the composition, like in the reference |
| Illustration inside the zone/dome | full-fledged sprite from the reference, not a single line |
| Colored Rim/Zone Accents | saturation as in the reference; compare with pipette, tolerance ±10% according to HSL |

## 5. Polish animation checklist (80% sense of quality)

1. The appearance of any objects - `Back.easeOut` or `Elastic.easeOut`; `Linear` prohibited for intro/feedback.
2. Squash & stretch when dropping cards: scale 1.06 → 0.97 → 1.0 in ~200 ms.
3. Success: burst 15–25 particles from the texture (star/spark) + short scale wave at the target; particles are event-related, not permanent.
4. Error: camera shake 2–3 px, 120–160 ms + coral backlight; without degrading effects.
5. Hover/focus on interactive objects: lift 4–6 px + shadow strengthening (second frame or scale of the shadow sprite).
6. Reduced motion: the same states through color/outline/icon, without camera and particles (the contract from the main plan is preserved).

## 6. Definition of Done visual (gate per game)

The game is considered visually ready only if all points are completed:

- [ ] not in the scene `Graphics`-decor (grep by renderer: `fillRect|fillRoundedRect|lineStyle` outside the interactive layer and masks);
- [ ] all panels are NineSlice made of satin;
- [ ] screenshot `output/playwright/<game>-phaser-final.png` placed next to the reference and goes through a line-by-line check: background contrast, depth/shadows, frame density, size and position of the mascot, branded details (domes/illustrations/arches);
- [ ] a numerical style guide (section 4) was completed for each parameter;
- [ ] polish checklist (section 5) completed;
- [ ] visual regression screenshots were taken for the idle/selected/correct/wrong/complete/mobile states and recorded as a reference;
- [ ] asset size and FPS budgets from the main plan are not violated;
- [ ] the asset origin registry is full.

Self-test “works” ≠ “looks like it”. Until each item on the check matches the reference, the game is not declared ready.

## 7. Pilot: group-sort as reference run

Work order (after the pilot the recipe is replicated for the remaining 5 games):

1. Make a list of art kit objects based on reference `design-references/group-sort/group-sort-light-arcade-v2.png`: background plate (v1 already available), 3 podiums with domes and illustrations (graph/atom/feather), card tray, card (nine-slice), corgi pedestal.
2. Generate each object via channel A (style reference = game reference), remove the background via rembg; take the particle addition from the Kenney Particle Pack (channel B).
3. Collect the atlas + manifest, put it in `public/game-assets/games/group-sort/`.
4. Rewrite the scene: remove Graphics decor, mount sprites, enable NineSlice for cards and tray.
5. Go through the polish checklist (section 5).
6. Run the autonomous quality contour (section 11) until the judge’s green verdict, then Definition of Done (section 6) with a screenshot comparison.
7. Record the actual labor costs and rake at the end of this document, then go to quiz-rush → recall-deck → mistake-arena → force-lab → match-pairs.

## 9. Mascot

- Use existing corgi assets; a new unrelated mascot is not generated (rule from `GAME_REDESIGN_PIPELINE.md`).
- Target format: sprite sheet 5–7 states (idle/focus/drag/correct/wrong/complete) or Rive state machine (https://rive.app) if smooth transitions are required.
- Position and scale - according to the reference of a specific game, with a minimum from section 4.

## 10. Execution Rule

Any task “to improve the visuals of game X” begins with checking whether there is a complete art kit according to section 3. If not, the art kit is first produced (channels A/B/C), and only then the scene code is changed. Iterations “tweak the primitives to make it more beautiful” are prohibited as a class of work.

## 11. Autonomous quality circuit (vision judge)

The process is completely autonomous: the product owner does not participate in iterations, only accepts the final result. The role of the “eye” is performed by a separate vision call to the model as a critic. The code agent’s self-assessment of his own result is not considered a verdict.

### 11.1. Cycle

```text
build → playwright screenshot (idle/correct/wrong/complete, desktop+mobile)
  → vision judge: [screenshot + reference + rubric] → JSON verdict
  → if all criteria ≥ 8/10 → fix standards, DoD (section 6)
  → else → apply specific corrections from the verdict → repeat
Limit: 6 iterations per game. When exhausted, stop and report to the owner with the final verdict.
```

### 11.2. Judge's rubric (prompt contract)

The judge is given two images (screenshot, reference) and instructions:

> You are a strict art director of casual games. Compare SCREENSHOT with REFERENCE. Rate each criterion 0–10 and return strictly JSON:
> `{"background_contrast":n,"depth_shadows":n,"composition_density":n,"mascot_presence":n,"signature_details":n,"style_unity":n,"fixes":["specific fix for each criterion < 8"]}`
> Criteria: background_contrast - the background is saturated and readable, not faded; depth_shadows — volume, shadows, chamfers as in the reference, no flat rectangles; composition_density - the frame is full, there are no large empty panels; mascot_presence - the mascot is noticeable in the composition, not a sticker in the corner; signature_details — domes/illustrations/arcs/podiums are present and detailed; style_unity - all elements in the same style, without alien ones. In fixes, write in detail: which object, what exactly to change.

### 11.3. Tournament of Options

For controversial decisions (composition, density, asset variant), 2-3 options are generated, the judge receives them in one set and selects the best one with justification. A tournament is preferable to sequential editing of one option.

### 11.4. Reference fixation and protection against degradation

- Screenshots that pass the judge are saved in `tests/visual-baselines/<game>/`.
- In CI the comparison is run (`expect(page).toHaveScreenshot()` or pixelmatch, tolerance ≤ 1% pixels); excess - red assembly.
- The standard is updated only through a new green verdict of the judge, not by manual rewriting.

### 11.5. Judge for individual assets

Before assembling the atlas, each generated asset undergoes a quick check by a judge on two points: compliance with the reference style and cleanliness of the cut (no halos/remnants of the background). Failed ones - regeneration, maximum 3 attempts, then fallback to CC0-pack (channel B).
